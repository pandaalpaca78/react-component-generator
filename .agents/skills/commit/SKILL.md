# Commit

변경사항을 논리적인 단위로 나누고 `feat/fix/refactor/chore: 한국어 요약` 형식으로 커밋한다. 사용자의 커밋 요청을 실행 승인으로 간주하고, 분석부터 커밋까지 별도 확인 없이 진행한다. 사용자가 검토나 계획만 요청한 경우에는 커밋하지 않는다.

## 1. 변경사항 분석

- `git rev-parse --show-toplevel`로 저장소를 확인하고 적용되는 `AGENTS.md`를 읽는다. 저장소가 아니면 상황을 알리고 중단한다. 임의로 `git init`하지 않는다.
- `git status --short`, `git diff --stat`, `git diff`, `git diff --cached`로 미스테이징·스테이징 변경을 함께 확인한다. 추적되지 않은 파일은 내용을 직접 확인한다.
- 변경이 없으면 커밋할 내용이 없다고 알리고 종료한다.
- 기존 스테이징 상태와 사용자 변경을 존중한다. 요청 범위 밖 변경, 키·토큰 등 비밀정보, 의도하지 않은 생성 파일을 커밋 대상에 섞지 않는다.

## 2. 논리적 단위로 분류

- 파일 종류가 아니라 목적과 의존 관계를 기준으로 묶는다. 하나의 기능에 필요한 구현·스타일·테스트는 함께 묶고, 독립적인 수정은 분리한다.
- 같은 파일에 독립적인 변경이 섞이면 필요한 헝크만 스테이징할 계획을 세운다. 안전하게 분리할 수 없다면 원본을 훼손하지 말고 분류의 한계를 설명한다.
- 변경에 필요한 검증을 수행하고 결과를 정리한다. 실행하지 못했거나 실패한 검증은 그대로 밝힌다.

## 3. 한국어 메시지 작성

각 커밋의 포함 파일·변경 요약·검증 결과와 정확한 메시지를 정리한다. 계획을 간단히 알린 뒤 승인 대기 없이 실행한다.

- `feat: 프로필 카드 생성 기능 추가` — 새로운 기능
- `fix: 빈 프롬프트 제출 오류 수정` — 버그 수정
- `refactor: 컴포넌트 생성 로직 분리` — 동작을 유지하는 구조 개선
- `chore: 개발 도구 설정 정리` — 도구·설정·유지보수

타입은 위 네 가지 중 변경 목적에 맞게 고르고, 요약은 한국어로 간결하게 쓴다. 본문이 필요하면 변경 이유와 주요 내용을 한국어로 덧붙인다.

커밋 요청이 있으면 파일 분류와 메시지 선택은 스스로 결정한다. 별도 승인을 요청하지 않는다. 요청 범위를 판단할 수 없거나 관련 없는 스테이징 변경을 안전하게 분리할 수 없는 경우에만 필요한 정보를 질문한다.

## 4. 커밋 실행

- 실행 직전에 diff를 다시 확인한다. 변경이 추가되었으면 요청 범위에 맞게 분류와 메시지를 갱신하고 진행한다.
- 요청 범위에 해당하는 파일이나 헝크만 명시적으로 스테이징하고 `git diff --cached`로 실제 커밋 대상을 확인한다. 관련 없는 기존 스테이징 변경이 함께 포함되지 않도록 한다. 이를 안전하게 보장할 수 없으면 중단하고 이유를 설명한다.
- 작성한 한국어 메시지로 `git commit`한다. 여러 커밋은 의존 관계에 맞는 순서대로 실행한다.
- 훅이나 커밋이 실패하면 원인을 보고하고 중단한다. 임의로 훅을 건너뛰거나 `--amend`, 이력 재작성, 강제 작업을 하지 않는다.
- `git log -1 --format="%h %s"`와 `git status --short`로 결과를 확인하고 커밋 해시·메시지·남은 변경사항을 보고한다. 별도 요청 없이 push하지 않는다.
